# Research: Progress tracking and reporting

**Plan**: [plan.md](plan.md). Every API below was checked in `MOODLE_502_STABLE` source on 2026-10-02, after a Context7 query (`/websites/moodledev_io_5_2_apis`). In 5.1 and later core lives under `public/`; paths here leave that prefix off. "Inferred" marks a behaviour read from source but not run. Each **Verify** line is something to confirm on the 5.2.3+ instance, with test accounts only, before the task that depends on it is closed (constitution X).

## R1. One completion rule, stated in the payload and applied by the plugin

**Decision**: The rule is defined once, in `scripts/moodle_payload.py`, as plain data on each module and on the course. It says nothing about Moodle:

| Item | `completion` value | Means |
|---|---|---|
| A page (lesson, scenario bank, job aid, withheld-quiz placeholder) | `view` | complete when opened |
| A quiz with a pass mark | `pass` | complete when an attempt reaches the pass mark |
| A quiz without one | `submit` | complete when an attempt is submitted and graded |
| The course | `all` | complete when every published item is complete |

`local_ltuse` turns the values into Moodle settings: `completion = 2` (`COMPLETION_TRACKING_AUTOMATIC`) on every module; `completionview = 1` on a page; `completionusegrade = 1` on a quiz, and with it `completionpassgrade = 1` when `gradepass > 0`. The tracking constants are in `lib/completionlib.php`. `COMPLETION_CRITERIA_TYPE_ACTIVITY` (4), used in R3, is not: it is defined in `completion/criteria/completion_criteria.php:53`, which completionlib includes (:38).

The spec's Assumptions say that scenario banks and job aids count only if they are numbered as lessons. Every learner page the payload publishes is numbered already, because `module_key()` derives each idnumber from its file number. So "every published page" and "every numbered lesson" are the same set. The rule needs no exception list.

**Rationale**: Principle II keeps the payload platform-neutral, and a rule that says "view" and "pass" is about pedagogy, not about Moodle. Writing it in the payload means a second publish target would get the same rule. `create_quiz` already sets `gradepass` from the quiz's own threshold. That matters, because `gradepass > 0` is enforced only by the module form (`course/moodleform_mod.php` ~414–437), which `add_moduleinfo()` never runs. With `gradepass = 0`, `completion_info::internal_get_grade_state()` returns plain complete for any grade. That is why a quiz with no pass mark is `submit`, never `pass`.

**Alternatives considered**: A `moodle/site/completion.yaml` the publisher reads. That would put a per-course rule into site configuration, and the rule would then know Moodle field names. Site-level default completion (`core_completion` default activity completion, `course/defaultcompletion.php`). That would set the rule per module type, site-wide, and nothing in the repo would show it.

## R2. Activity completion: set on create, unlocked only from "not tracked"

**Decision**: `util::upsert_module()` takes the completion fields from the caller instead of hard-coding `completion = 0`.
- **On create**, `add_moduleinfo()` writes them as given.
- **On update**, `update_moduleinfo()` (`course/modlib.php` ~657–672) ignores the cm completion fields unless `$moduleinfo->completionunlocked` is set. Setting it calls `completion_info::reset_all_state($cm)`, which deletes every learner's state for that module and, if the module is a course criterion, every course completion in the course (`delete_all_state()`). It then recomputes the module's state for every tracked user.

So the plugin sets `completionunlocked = 1` only when the module's current tracking is `COMPLETION_TRACKING_NONE` **and** the module is not an activity criterion of its course (no `course_completion_criteria` row with `criteriatype = 4` and `moduleinstance` = its cmid). Such a module has no learner state and no course completion depends on it, so the reset deletes nothing. A module whose tracking was turned off by hand while it is still a criterion fails the second test, and is reported `differs`: unlocking it would delete every course completion in the course. This is the one-time move for courses published before this spec.

If a module's tracking already differs from the rule, the plugin changes nothing and reports `completion-differs` in its result. The publisher prints that and exits 1. A change to the rule itself is therefore never silent. It needs its own reviewed migration, which would name the learners whose state it resets.

**Rationale**: FR-011. The only core path that changes a tracked module's completion settings resets learner state, so the plugin never takes it on a tracked module.

**Verify**: Republish a pre-spec course: its modules become tracked, and nothing else changes. Republish it again: no `completion-differs`, and no state is reset (a test learner's ticks stay). Edit one page's completion by hand to manual, then republish: the publish exits 1 and names that module.

**Alternatives considered**: Always sending `completionunlocked`, which wipes progress on every publish. Never sending it, which leaves every pre-spec module untracked for good.

**Confirmed in source (T001)**:
- **Constants** (`lib/completionlib.php`): `COMPLETION_TRACKING_NONE = 0` (:56), `MANUAL = 1` (:62), `AUTOMATIC = 2` (:67); `COMPLETION_VIEW_REQUIRED = 1` (:112); `COMPLETION_COMPLETE = 1`, `COMPLETION_COMPLETE_PASS = 2`, `COMPLETION_COMPLETE_FAIL = 3` (:79–89); `COMPLETION_AGGREGATION_ALL = 1` (:144).
- **Create writes completion only when completion is on.** `add_moduleinfo()` (`course/modlib.php:83–94`) copies `completion`, `completionpassgrade`, `completiongradeitemnumber`, `completionview` and `completionexpected` onto the new cm only inside `if ($completion->is_enabled())`, which needs both the site switch and the course's `enablecompletion` (`completion_info::is_enabled()`, `lib/completionlib.php:296–321`). `update_moduleinfo()` has the same gate (:656–657). Otherwise the fields are dropped with no error. So `ensure_course` must send `enablecompletion: 1` before any `create_page` or `create_quiz` call, and the plugin must not report `set` unless `is_enabled()` is true: it refuses, or reports something other than `set`.
- **`completionusegrade` is converted, not stored.** The cm has `completion`, `completiongradeitemnumber`, `completionview`, `completionexpected` and `completionpassgrade` (`lib/db/install.xml:339–343`), and no `completionusegrade` column. `set_moduleinfo_defaults()` (`course/modlib.php:487–507`) turns `completionusegrade = 1` into `completiongradeitemnumber = 0` when no item number is set. When neither is set, it forces `completionpassgrade = 0` and `completiongradeitemnumber = null`. "Equals the rule" is therefore read as: `view` is `completion = 2, completionview = 1, completiongradeitemnumber` null; `submit` is `completion = 2`, item number not null, `completionpassgrade = 0`; `pass` the same with `completionpassgrade = 1`. DB values arrive as strings.
- **Update path.** `update_moduleinfo()` (`course/modlib.php:656–673`) writes `completion`, `completionpassgrade`, `completiongradeitemnumber` and `completionview` only when `!empty($moduleinfo->completionunlocked)`. It nulls the grade item number when `completionusegrade` is empty, so `completionusegrade` must be in the data. It then rebuilds the course cache and calls `reset_all_state($cminfo)` (:790–798).
- **`reset_all_state()`** (`lib/completionlib.php:963–992`), for an automatic cm, collects the users with state, calls `delete_all_state($cm)`, then calls `update_state($cm, COMPLETION_UNKNOWN, $u)` for every tracked user. `delete_all_state()` (:923–948) deletes the cm's `course_modules_completion` rows. If the cm is an activity criterion, it also deletes that criterion's `course_completion_crit_compl` rows and every `course_completions` row in the course, completed ones included (:939–943). That is why the guard above has its second test.
- **Page views from before this spec get no credit.** A `view` rule reads `course_modules_viewed` (`get_core_completion_state()`, :1177–1182). That table is written only by `internal_set_data()` (:1255–1267), and `set_module_viewed()` returns early while `completionview` is off (:799). So no row exists for earlier views, and `reset_all_state()` computes those pages as incomplete. Learners must reopen earlier lessons after the first post-spec publish, and US1's Verify step should expect it. Quiz grades from before this spec do count, because the grade rule reads the existing grade (`get_grade_completion()`, :748–776).
- **`get_moduleinfo_data()`** (`course/modlib.php:856–861`) fills `completion`, `completionview`, `completionexpected`, `completionusegrade` (`is_null(completiongradeitemnumber) ? 0 : 1`), `completionpassgrade` and `completiongradeitemnumber` from the current cm. `util::upsert_module()` overlays the caller's `$fields` on it, so the caller's completion fields win, but they are still ignored without `completionunlocked`.
- **Quiz on 5.2.** `completionpassgrade` is a `course_modules` column. The `quiz` table holds only `completionattemptsexhausted` and `completionminattempts` (`mod/quiz/db/install.xml:48–49`). When `completionunlocked` is set, `quiz_process_options()` (`mod/quiz/lib.php:1058–1070`) zeroes `completionpassgrade` if `completionusegrade` is empty, and `completionminattempts` if `completionminattemptsenabled` is empty.
- **Pass mark.** It lives on the grade item, written by `edit_module_post_actions()` from `$moduleinfo->gradepass` (`course/modlib.php:301–306`). The `> 0` check is form-only (`course/moodleform_mod.php:414–440`). `internal_get_grade_state()` (`lib/completionlib.php:1584–1620`) returns plain `COMPLETION_COMPLETE` for any grade when `gradepass` is 0. With `gradepass > 0` and `completionpassgrade`, a failing grade gives `COMPLETION_COMPLETE_FAIL` (:1156–1173, reduced at :725–734). A failed attempt shows as "complete, failed" on the activity but does not satisfy a course criterion: the cron SQL needs `PASS` when `cm.completionpassgrade = 1` (`completion/classes/api.php:152–157`), and `review()` accepts only `COMPLETE` or `COMPLETE_PASS` (`completion/criteria/completion_criteria_activity.php:159`).
- **No conditions at all.** An automatic cm with no condition is complete at its first evaluation (`internal_get_state()`, :693, :721). The plugin never sends `completion = 2` without `completionview` or `completionusegrade`.
- **Repo.** `create_page`'s `unchanged` short-circuit (`moodle/local_ltuse/classes/external/create_page.php:106–115`) returns before `upsert_module()`, so a pre-spec page with unchanged content would never get tracking. `is_unchanged()` must return false when a rule was sent and the cm's tracking is `NONE`, and the short-circuit must still fill the new `completion` result (`unchanged` or `differs`). On create, `create_page` calls `upsert_module()` twice (:149–160). The second call updates a module that is already tracked, so it must return `unchanged`, not `differs`.

## R3. Course completion criteria: our own diff, never `clear_criteria()`

**Decision**: There is no API function for course completion criteria. `course/completion.php` is the only implementation, and it starts with `$completion->clear_criteria(false)`. That calls `delete_course_completion_data()`, which deletes every `course_completions` and `course_completion_crit_compl` row in the course. The form's "lock" is only UI (`completion_form`, `hardFreezeAllVisibleExcept`).

A new `local_ltuse_set_course_completion` function therefore makes the change itself, through core's completion classes and never through raw SQL:
- The **wanted set** is every visible module in the course with an `ltct:<slug>:` idnumber. Hidden modules, which the publisher hides when the repo drops them, are left out. Since `update_state()` has no visibility gate, a hidden criterion would stay required, and nobody could complete the course (inferred, 1f). The question bank is never in the set.
- **New criteria** become `completion_criteria_activity` objects, inserted one by one with `insert()`. That is the same data object `update_config()` builds (`completion/criteria/completion_criteria_activity.php`). `module` is the module's name (`page`, `quiz`) and `moduleinstance` is its cmid, never `cm.instance`.
- **Criteria no longer wanted** are removed with the object's `delete()`. The present set is read from `course_completion_criteria` directly, not through `completion_info::get_criteria()` or `completion_criteria_activity::fetch()` (see below).
- **Aggregation** is `COMPLETION_AGGREGATION_ALL`, set overall and for `COMPLETION_CRITERIA_TYPE_ACTIVITY` through `completion_aggregation::setMethod()` and `save()`, as `course/completion.php` does.
- When anything changed, it fires `\core\event\course_completion_updated`, as the form does.
- When a criterion was removed, every incomplete `course_completions` row in the course is flagged for re-aggregation through the `completion_completion` data object: set `reaggregate = time()`, then call `mark_enrolled()`, whose `_save()` writes the row and refreshes the `coursecompletion` cache. That is core's own pattern (`lib/classes/task/completion_daily_task.php:115–126`). `mark_enrolled()` on its own flags nothing, and `mark_inprogress()` is not used, because it also sets `timestarted` to now. A learner who had done everything else is then marked complete by `completion_regular_task`. Rows that are already complete are not touched.

**What this gives the edge cases**:
- **A lesson is added.** A learner already complete keeps `timecompleted`. Nothing re-checks a completed row, so they stay complete. A learner in progress now has the new lesson outstanding.
- **A lesson is removed.** Its criterion goes. Learners in progress are re-checked, and anyone who had done everything else becomes complete.
- **A withheld quiz.** It is published as a page, so it is a `view` criterion and never blocks completion.

**Rationale**: FR-011 and the "republish never silently erases" edge case. After a wipe, core's daily task (`completion_daily_task`) only recreates the missing `course_completions` rows for enrolled users, which can take up to a day. The re-aggregation that would then mark a learner complete is `completion_regular_task`, which runs every minute (`lib/db/tasks.php:153–159`), and it works against the new criteria, so a learner who had finished could be shown incomplete again. Our diff never wipes anything.

**Principle XI**: The `completion_criteria_activity`, `completion_aggregation` and `completion_completion` classes are core's completion API (data objects in `lib/completionlib.php` and `completion/`). `course/completion.php` and `update_config()` use exactly them. Reading `course_completion_criteria` by `course` (indexed) to compute the diff is a read of a stable core table. Inserting through the data objects is the same write core's own form makes, not a raw table write. Removing a criterion without wiping completions has direct precedent: core's own module deletion does a plain `delete_records('course_completion_criteria', ['moduleinstance' => cmid, 'course' => …, 'criteriatype' => ACTIVITY])` and leaves `course_completions` and criterion completions alone (`course/format/classes/local/cmactions.php:355–359`). The README still lists it, because a future refactor of course completion is the first place an upgrade would break us.

**Verify**: The edge-case table above, with test learners A (complete), B (two of three lessons done) and C (nothing done). Add a lesson and republish: A stays complete with the same date, and B and C have one more item to do. Remove a lesson B had not done and republish: after the next `completion_regular_task`, B is complete with the right date. Then check that `course_completions` for A was never deleted, by its id.

**Alternatives considered**: Calling `course/completion.php`'s sequence, which wipes completions on every republish that changes a lesson. Criteria set only on first publish, which breaks as soon as a lesson is added or removed (FR-002). Course completion by "all activities with completion" through a third-party plugin, which isn't needed when the diff is this small.

**Confirmed in source (T001)**:
- **`course/completion.php` sequence**: `delete_course_completion_data()` when unlocking (:91); `$completion->clear_criteria(false)` (:98); each type's `update_config($data)` (:100–106); overall aggregation as `new completion_aggregation(['course' => id, 'criteriatype' => null])`, `setMethod()`, `save()` (:108–115); activity aggregation the same way with `COMPLETION_CRITERIA_TYPE_ACTIVITY` (:121–125), then course (:133–135) and role (:143–145); then the event (:148–153).
- **What not to call.** `clear_criteria(bool $removetypecriteria = true)` (`lib/completionlib.php:494–513`) deletes every criterion and aggregation row for the course, then calls `delete_course_completion_data()` (:885–894), which deletes all `course_completions` and `course_completion_crit_compl` rows for the course and purges the `completion` and `coursecompletion` caches.
- **Includes.** `COMPLETION_CRITERIA_TYPE_ACTIVITY = 4` is in `completion/criteria/completion_criteria.php:53` (`$COMPLETION_CRITERIA_TYPES` at :84–94), which completionlib `require_once`s (:38). `completion_criteria_activity` itself is not autoloaded, and completionlib does not include it (only `internal_set_data()` does, at :1240). `set_course_completion.php` must `require_once($CFG->dirroot . '/completion/criteria/completion_criteria_activity.php')`, as `course/completion.php:34` does.
- **Criterion fields** (`completion/criteria/completion_criteria.php:109–159`, table `course_completion_criteria`): `id, course, criteriatype, module, moduleinstance, courseinstance, enrolperiod, timeend, gradepass, role`. `criteriatype` defaults to 4 in the activity class (`completion_criteria_activity.php:43`). `module` is the module name (char 100) and `moduleinstance` is the cmid (`lib/db/install.xml:166–167`; `update_config()`, `completion_criteria_activity.php:80–100`, sets `module = get_mod_name($cm->module)`, `moduleinstance = cmid`, `id = null`, then `insert()`). The table has only a non-unique index on `course` (`lib/db/install.xml:177–179`), so duplicate rows for one cm are possible, and `criteria_diff` de-duplicates the present set.
- **`insert()` and `delete()`** come from `data_object` (`completion/data_object.php:327–347`, `:281–299`). `insert()` refuses if `id` is set. `delete()` deletes that row only and leaves its `course_completion_crit_compl` rows behind. That is harmless: aggregation starts from `course_completion_criteria` with an inner join (`lib/completionlib.php:1764–1772`), so orphan criterion completions are ignored.
- **Reading the present set.** `completion_criteria_activity::fetch($params)` (:51–54) goes through `fetch_helper()`, which throws `morethanonerecordinfetch` on more than one match (`data_object.php:190–201`). `fetch_all()` on the criteria base is an empty stub returning null (`completion_criteria.php:167`). `completion_info::get_criteria()` caches on the instance and drops rows whose cm no longer exists (`lib/completionlib.php:405–446`, filter at :423–429), so orphans would never be removed. The plugin reads `$DB->get_records('course_completion_criteria', ['course' => $id, 'criteriatype' => COMPLETION_CRITERIA_TYPE_ACTIVITY])` and builds each with `new completion_criteria_activity((array) $row, false)` (or `completion_criteria::factory()`, :175–186) before calling `delete()`.
- **`completion_aggregation`** (`completion/completion_aggregation.php`, table `course_completion_aggr_methd`, unique on course + criteriatype). The constructor (`data_object.php:89–134`) loads the existing row; a null `criteriatype` becomes `IS NULL` (:226–231). `setMethod()` (:92–103) accepts ALL or ANY and falls back to ALL. `save()` (:112–118) updates or inserts. `completion_info::get_aggregation_method()` (`lib/completionlib.php:474–487`) returns ALL when no row exists, so `aggregation: unchanged` is decided from the loaded object's `id` and `method`, not from that.
- **The re-aggregation flag** is `reaggregate` on `completion_completion` (`completion/completion_completion.php:46`, :67; `lib/db/install.xml:210`). `mark_enrolled()` (:108–121) sets only `timeenrolled` when null, and leaves an existing value (`'0'` in the DB, not null) alone. `mark_inprogress()` (:130–149) sets `reaggregate` but also `timestarted`. The `fetch()` cache key needs both `userid` and `course` (:78–90). So: `$cc = new completion_completion(['userid' => $u, 'course' => $c]); if ($cc->id && !$cc->timecompleted) { $cc->reaggregate = time(); $cc->mark_enrolled(); }`.
- **Who consumes it.** `aggregate_completions(int $coursecompletionid, bool $mtraceprogress = false)` (`lib/completionlib.php:1754–1898`) takes every incomplete row with `reaggregate > 0 AND reaggregate < <task start>` in a course with `enablecompletion = 1`. It aggregates activity criteria by the activity method, folds that into the overall method, and on success calls `mark_complete()` with the latest criterion completion time (:1823–1828, :1864–1868). It then resets `reaggregate = 0` (:1885–1897). It is run by `\core\task\completion_regular_task::execute()` (`lib/classes/task/completion_regular_task.php:46–69`), after each criteria type's `cron()` (for activities `\core_completion\api::mark_course_completions_activity_criteria()`, `completion/classes/api.php:133–189`), **every minute** (`lib/db/tasks.php:153–159`). So "after the next `completion_regular_task`" means within a minute or two on a healthy cron.
- **A completed row is never changed.** `mark_complete()` leaves an existing `timecompleted` alone (`completion_completion.php:158–165`), and `aggregate_completions` filters `timecompleted IS NULL`. That confirms "A stays complete with the same date".
- **No visibility gate.** Neither the aggregation SQL (:1764–1772) nor `mark_course_completions_activity_criteria()` (`api.php:137–157`) looks at `cm.visible`, and `get_criteria()` drops only cms that no longer exist. That confirms inferred point 1f: a hidden criterion stays required.
- **Removing a criterion triggers nothing by itself.** `internal_set_data()` (:1298–1307) aggregates one learner at once only when a new criterion completion is created. That is why the `reaggregate` flag is needed.
- **`\core\event\course_completion_updated`** (`lib/classes/event/course_completion_updated.php:37–73`): crud `u`, no `objectid`, created with only `courseid` and `context` (`course/completion.php:148–153`). Core has no observer for it; it is for logging.

## R4. Completion is switched on at site and course level

**Decision**: These are declared in `settings/completion.yaml` (#7):
- `enablecompletion = 1`, the site switch (`completion_info::is_enabled_for_site()`);
- `moodlecourse/enablecompletion = 1`, the default for new courses;
- `moodlecourse/showcompletionconditions = 1`, so a learner sees on the course page what each lesson needs. Neither web service takes it, but `create_course()` reads it from `moodlecourse` (`course/lib.php` ~1814).

The publisher also sends `enablecompletion: 1` in both `core_course_create_courses` and `core_course_update_courses`, so a course published before this spec is switched on at its next publish.

The update web service has a bug: its site-disabled guard checks `enabledcompletion`, with a stray "d" (`course/externallib.php`), so it never fires. The site switch therefore has to come from the declaration. Drift reports it if someone turns it off.

**Verify**: Republish one pre-spec course: its course settings show completion on, and nothing was set by hand (US1-4).

**Confirmed in source (T001)**:
- `completion_info::is_enabled_for_site()` is `!empty($CFG->enablecompletion)` (`lib/completionlib.php:281–284`). `is_enabled($cm = null)` (:296–321) checks the site flag, then `$this->course->enablecompletion`, re-reading the course only if the property is missing, then returns `$cm->completion` for a cm. It must be given a course record read after `core_course_update_courses` has run. `util::course_by_idnumber()` re-reads the course on every web-service call, so this holds today.
- **Create**: `enablecompletion` is `VALUE_OPTIONAL` (`course/externallib.php:976`). With the site switch on, a missing value defaults to `moodlecourse/enablecompletion`; with it off, the value is forced to 0 silently (:1084–1092). `create_course()` then fills `showcompletionconditions` from `moodlecourse/showcompletionconditions` when completion is on, and unsets it when off (`course/lib.php:1810–1821`). `create_courses` runs in one delegated transaction (:1025, :1123).
- **Update**: the guard is `if (array_key_exists('enabledcompletion', $course) && !completion_info::is_enabled_for_site())` (:1305–1307). The typo means it never fires, so `enablecompletion: 1` is written even with the site switch off, as above.
- **`update_courses` reports failures as warnings.** It has no transaction, and turns a per-course exception (a missing capability, say) into a `warnings[{item, itemid, warningcode, message}]` entry (:1338–1350), not an error. `ensure_course` ignores the response today (`scripts/publish_moodle.py:106`), so a refused update of `enablecompletion` or of the custom fields passes silently. The publisher must treat a non-empty `warnings` as a failure.
- **`showcompletionconditions` is not a web-service parameter** (create params :926–1000, update params :1151–1210), and `update_course()` leaves it alone unless completion is being switched off (`course/lib.php:2014–2016`). A course first created while completion was off keeps `showcompletionconditions = NULL` after a republish sends `enablecompletion: 1`, so US2's Done/To-do stays hidden. The site defaults are 1 for `enablecompletion` (`admin/settings/subsystems.php:26–28`), `moodlecourse/enablecompletion` and `moodlecourse/showcompletionconditions` (`admin/settings/courses.php:247–254`), so this bites only if completion was ever switched off. Either the plan records that limit, or `local_ltuse_set_course_completion` sets the column through `update_course()`.

## R5. Offline completion from the Moodle app

**Decision**: Nothing to build. The app sends `mod_page_view_page` when a learner opens a page. Offline, `CoreCourseLogHelper` stores the call and syncs it later (moodleapp `src/core/features/course/services/log-helper.ts`). On the server, `page_view()` calls `completion_info::set_module_viewed()`. Quizzes go offline because `create_quiz` already sets `allowofflineattempts = 1` (spec 009). A synced attempt is graded on the server, which sets the quiz's completion.

**Dating**: The completion's `timemodified` is the time the server received the sync, not the time the learner opened the page offline (inferred). The spec says "dated when they happened where the platform allows", and here it does not. Reports show the sync time, and the plan says so rather than claiming otherwise. This was accepted on 2026-10-02 (plan "Decisions on the plan's limits", #5).

**Verify** (blocks US1's checkpoint, FR-003): On an Android device with a test learner, download a course, go offline, open two pages and submit the quiz. Reconnect, then check that all three appear in the completion report and that the course progress bar moves. Record the device, app version and the dates shown. Run this with spec 009's V7 so the device is set up once.

## R6. Learners see their progress on My courses

**Decision**: Core does this once completion is on. `block_myoverview` shows a progress bar per course from `core_completion\progress::get_course_progress_percentage()`. That counts only visible tracked activities, and returns 100 for a complete course. `course_classify_for_timeline()` (`course/lib.php` ~3279) puts a complete course under **Past**, so the **In progress** view never mixes it in (US2-2).

The learner's route to their next lesson is the course page. With `showcompletionconditions` on and the topics format, each lesson shows its "Done" or "To do" state, and the course index marks the same.

**The gap**: Core has no "continue where you left off" link that goes straight to the next incomplete lesson. Acceptance scenario US2-1 asks for one, and this plan does not build it. It is a learner-experience question, so it goes to spec 007 (#13), which owns the dashboard. US2 is not marked done until SC-004's real learners have tried the core route. If they cannot find their next lesson within a minute, 007 adds the link. The plan records this rather than quietly meeting a weaker criterion.

**Status**: The maintainer has not yet confirmed this gap (plan "Decisions on the plan's limits", #1).

**Verify**: The block's admin settings for which groupings are offered (`block_myoverview/displaygroupingall` and its siblings), and which grouping a learner sees first when "All" is not offered. If hiding "All" makes "In progress" the first view, `settings/completion.yaml` declares it. If not, the default stays and 007 decides.

## R7. Report builder has no viewer scoping, so there is one report per organisation

**Decision**: Custom reports never filter rows by who is looking. Neither `datasource.php` nor the participants datasource references `$USER`. The only viewer-relative condition is `user:userselect` with `USER_CURRENT`, which means "this row is me". Profile-field conditions compare only against a fixed value. There is no "same `ltct_org` as the viewer" and no "shares a group with the viewer".

So, as spec 002 does for cohorts, **each organisation gets its own report, generated from its entry in `organisations.yaml`**:
- **Fixed conditions**, which a viewer cannot change:
  - `user:profilefield_ltct_org` equal to the key; **Amended by spec 016 decision 2 option (a) (Doug, 2026-10-05 (scope review)):** the scope condition is `cohort:idnumber = ltct:org:{org}`, a text condition; the Organisation column is dropped; `validate` refuses `user:profilefield_ltct_org` conditions.
  - `role:name` is `student`, so the organisation's managers and any teacher are not listed as learners. The stored value is the student role's id, resolved by shortname at apply (R10);
  - `enrol:plugin` is `cohort`, which separates delivery from pilots (R10). **Amended by spec 002 R10 (2026-10-05 note; a0389bc, PR #92):** the condition is `enrol:plugin` not equal to `manual`, so cohort sync and a manager's enrolment through the organisation-enrolment instance (`enrol_self`) both count, and a pilot's manual enrolment never does (`moodle/site/reports.yaml` `progress` conditions; `SCOPE_CONDITIONS` in `scripts/site_config.py`). See R10's amendment.
- **Audience**: `core_cohort\reportbuilder\audience\cohortmember` with the organisation's managers cohort, `ltct:org:<key>:managers`.
- **Filters**: a viewer can only narrow, because filters are ANDed with the conditions. Picking a course, a date or a learner name can never reach another organisation's rows (US3-2).

**Why the profile field and not the cohort or the group**: 002's R9 makes `ltct_org` the source of truth for membership. A learner who moves therefore leaves their old organisation's report the moment the field changes, even while their old, suspended enrolment and group membership remain. Their earlier completions move with them, because a course completion is one record per learner per course, not per enrolment (002 R7). That is spec 002's decision, which the spec's edge case defers to.

> **Superseded by spec 016 research R11 (Doug, 2026-10-05 (scope review), decision 2 option (a); d395494, PR #84).** The scope is the organisation's member cohort, `cohort:idnumber` equal to `ltct:org:<key>`, not the profile field. Report builder offers a profile-field condition only while the field is visible and silently skips one that is unavailable, so a scope on `ltct_org` would widen the moment the field was hidden; a missing cohort matches nobody, so the cohort condition fails closed. A learner who moves still leaves their old organisation's report and joins the new one, because `ltct:org:<key>` is a `tool_dynamic_cohorts` cohort whose rule is `ltct_org` equal to the key (spec 002 R4): report membership follows that cohort rule, as the plugin applies it, rather than the field directly. The completion record still moves with them, as above.

**Cohort managers**: spec 002 defines no cohort other than the organisation cohort, so a cohort's scope is its organisation's. US3-3 is met by the same report. A future sub-organisation cohort would get its own generated report the same way.

**Viewing a report**: `permission::can_view_report()` checks `moodle/reportbuilder:viewall`, then the edit capabilities, then audience membership. `moodle/reportbuilder:view` has archetype `user`, so every signed-in user has it, and the audience is what decides. No capability is added to `orgmanager` for this.

**Verify** (blocks US3's checkpoint, SC-002). Use 002's two test organisations, A and B, in two shared test courses. As manager A:
- open the A report and count the rows: A learners only;
- open the B report by id: refused;
- apply every filter, including clearing them all: no B row;
- download the report as CSV and as Excel: the same rows;
- call `core_reportbuilder_retrieve_report` and `core_reportbuilder_list_reports` with the manager's own token: only the A report.

Then move one A learner to B: they leave A's report and appear in B's. Repeat as manager B. Record the result outside the repo tree.

**Alternatives considered**:
- A `local_ltuse` report builder datasource with a viewer-relative condition ("the viewer manages this row's organisation"). One shared report would cover every organisation. But it would be our code on the most sensitive path, for a gain the generator already gives.
- Core's per-course completion reports alone (R8). They are group-scoped, but cover one course at a time, and can't be scheduled.
- Report builder's `categoryrole` audience, which does not exist in core (agent search across all subsystems).

## R8. Managers also get core's per-course completion reports

**Decision**: `orgmanager` gains `report/progress:view` and `report/completion:view`. Both are course-context capabilities. `report/progress/index.php` and `report/completion/index.php` honour separate groups: without `moodle/site:accessallgroups`, which `orgmanager` lacks (002 R2), they show only the viewer's group.

These two reports give what report builder cannot: a tick per lesson and the quiz's pass or fail. Both offer a spreadsheet download.

**Rationale**: FR-006 asks for "lessons completed of total" and a "quiz result". In report builder, the participants datasource has no per-activity completion entity and no quiz grade. Its `completion` entity has `progresspercent` and `grade`, the course total. So the cross-course report shows progress as a percentage, and the course total, which is the quiz grade, since pages carry no grade. The in-course reports show the per-lesson detail. Both views are scoped, one by configuration and one by groups. Showing progress as a percentage in the cross-course report was accepted on 2026-10-02 (plan "Decisions on the plan's limits", #3).

> **Amended 2026-10-05 (spec 002 open courses, PR #86; 002 R2 and spec 002 plan, cross-spec "004" follow-ups).** Shared courses have no organisation groups, and the managers cohort is no longer enrolled in them, because with no groups `orgmanager`'s two report capabilities would show every organisation's learners (002 R2, citing `report/progress/index.php:99-110` and `report/completion/index.php:85-86`). `orgmanager` is enrolled only in organisation-only courses, where every learner is the organisation's, so its course-wide reach is already scoped. A manager therefore has the in-course reports only in an organisation-only course; in a shared course they follow their people through the organisation report (R7) and spec 002's "my organisation" page. The decision above and the Verify below are kept as written for the record; quickstart V6 now runs in an organisation-only course.

**Verify**: As manager A in a shared course, both reports list A's group only, and asking for group 0 or B's group id in the URL is refused. The download holds the same rows. 002's moved-learner limit applies here too: until the site team removes the suspended A enrolment, the moved learner still shows on A's in-course reports. That is the same known limit 002 records, now on two more pages.

**Alternatives considered**: `moodle/grade:viewall` for the gradebook. That isn't needed, because the completion report already shows the quiz state, and it would add another page to keep group-scoped.

## R9. Reports, audiences and schedules are created by the applier

**Decision**: There is no web service that creates a report, an audience or a schedule. `core_reportbuilder_*` covers columns, conditions, filters and reading. So `site_config.py`'s applier gains a `reports` item type, in a new `local_ltuse\siteconfig\reports` class. It uses core's helpers:
- `core_reportbuilder\local\helpers\report::create_report()` with `default = false`, so we decide the columns;
- `add_report_column()`, `add_report_condition()` and `add_report_filter()`;
- `base::set_condition_values()`;
- `core_reportbuilder\local\audiences\base::create()`;
- `core_reportbuilder\local\schedules\base::create()` with the `message` type. Not the deprecated `helpers\schedule::create_schedule()` (MDL-86066).

**Identity**: A report has no `idnumber`. Its persistent does carry `component`, `area` and `itemid`. The applier sets `component = local_ltuse` and `area` to an encoding of the report's key, and finds the report by that pair. `area` is `PARAM_AREA`, so it must match `^[a-z](?:[a-z0-9_](?!__))*[a-z0-9]+$`: no colon, no hyphen. An organisation report's area is therefore `org_<org key>_<key>` and any other report's is `<key>`, with every `-` turned into `_` (for example `org_seed_company_progress`, `competency_coverage`). `validate` fails when an expanded area does not match the pattern, and when two areas collide after encoding (org `a-b` with template `c`, and org `a` with template `b-c`, both give `org_a_b_c`). The custom reports list does not filter on `component` (confirmed below), so the reports still appear there.

There is no unique index on (`component`, `area`), and a report duplicated in the UI keeps both. So more than one match is reported as an error, and the applier never updates an arbitrary one of them.

**What apply does**, keeping spec 001's rules:
- A missing report is created.
- A declared report whose columns, conditions, filters, audiences or schedule differ is brought back to the declaration, and drift reports it as `changed`. A report has no learner data in its definition, so correcting it loses nothing.
- A `local_ltuse` report that is no longer declared is reported as `extra` and kept.

**Verify**: That a report with `component = local_ltuse` is listed and viewable at `reportbuilder/index.php` for its audience, and editable by the site team. That `apply` twice changes nothing. That a column renamed by hand shows as drift. Audience access is cached per user for 30 minutes (below), so purge caches after changing a test manager's cohort membership, or allow for the delay.

**Alternatives considered**:
- Identity by report name, which breaks on a rename.
- Report tags. They can be edited by anyone who can edit the report, so they are not a stable identity.
- Building reports by hand once and exporting them. Core has no report export or import, and it would fail SC-005.

**Confirmed in source (T001)**:
- **No web service creates a report, an audience or a schedule.** `lib/db/services.php:3063–3226` registers only `core_reportbuilder_` list, retrieve, view and delete; columns add, delete, reorder and sort; conditions and filters add, delete, reorder and reset; `audiences_delete`; and `schedules_delete`, `send` and `toggle`. The applier has to use the PHP helpers.
- **`helpers\report`** (`reportbuilder/classes/local/helpers/report.php`):
  - `create_report(stdClass $data, bool $default = true): report_model` (:47) trims the name, forces `type = TYPE_CUSTOM_REPORT` and calls `manager::create_report_persistent()`. With `$default = false` it adds no columns, filters or conditions. Unknown properties are dropped silently by `persistent::properties_filter()`.
  - `update_report($data)` (:83) needs `id`, `name` and `uniquerows`.
  - `add_report_column(int $reportid, string $uniqueidentifier): column` (:223), `delete_report_column` (:249), `reorder_report_column(int, int, int $position)` (:280, 1-based), `reorder_report_column_sorting` (:304), `toggle_report_column_sorting(int $reportid, int $columnid, bool $enabled, int $direction = SORT_ASC)` (:329).

- **The reports list does not filter on component.** `local/systemreports/reports_list.php:63` filters only `rb.type = TYPE_CUSTOM_REPORT`, plus the access SQL at :70.
- The report persistent's `before_delete` deletes the report's columns, filters, user filters, audiences and schedules.
- **Permissions.** `moodle/reportbuilder:view` defaults to `user => CAP_ALLOW` (`lib/db/access.php:2721`). `can_view_report` is view or viewall, then viewall, edit rights or audience membership. `can_edit_report` is `edit` for your own report, `editall` for anyone else's. Nothing is visible unless `$CFG->enablecustomreports` is set.
- **Audience cache.** The audience-to-reports map is cached per user in `core/reportbuilder_allowed_reports` (application cache, ttl 1800, `lib/db/caches.php`). **Plugin conventions for the new item classes** (repo, `moodle/local_ltuse/classes/siteconfig/`):
- `profilefields.php` is the model for `coursefields`: a class docblock that says what it checks, its identity, the core APIs it writes through and a "learner data is never touched" paragraph; sections for checking, applying, pure comparisons, reads and results. `check(): array` writes nothing and returns results in apply order. `apply(report $report): void` re-checks, writes only on `missing` or `changed`, re-checks again, and reports `'written, but the server still differs'` on failure. A static `result(...)` returns `{type, item, result, declared, live, message, secret: false, blocking}`.
- A category is found by exact name with a PHP re-check, because the collation may fold case (`find_categories`, profilefields.php:451): more than one is blocking `ambiguous`, none is `missing` ('apply will create it'). A field is found by exact shortname (`find_field`, :465); a wrong type is blocking `wrong-datatype`; differences render as `'differs: ' . implode(', ', keys)`.
- Undeclared owned items are reported by drift.php's `report_extra_owned()` (:72), found by prefix through `owned_records()` (case-sensitive `sql_like` plus a PHP re-check), e.g. `add('fail', 'extra', …, 'no longer declared in profile-fields.yaml; kept, never deleted')`. In apply an extra is `add_result($extra, 'skip')`.
- `report->add(string $status, string $kind, string $subject, $declared = null, $live = null, string $message = '', $setting = null)` (report.php:225). Statuses are `ok, changed, fail, skip`. `report::KINDS` has no `created`: a creation is printed as status `changed`, kind `missing`, message `created` (profilefields.php:220, :247; applier.php:136). A subject matching `/pass|secret|token|key|salt/i` is redacted, so subjects must avoid those words. `org:` subjects are fine.
- `applier.php:61` still calls `inspector::has_blocking()` (inspector.php:334), which treats any non-empty `blocking`, `report::BLOCKS_REPORT` included, as a run-wide block. The "blocks the report, not the run" rule needs the applier to use `report::has_blocking($preflight)` for the run and `report::has_blocking($preflight, $area)` per report, or `inspector::has_blocking()` must delegate to it.

## R10. Pilot learners are enrolled manually, delivery learners by cohort

**Decision**: A pilot and the published course are the same Moodle course, `ltct:<slug>`. A course is not re-published to a new one at stage 8. So the pilot cannot be told apart by course. It is told apart by **how the learner was enrolled**. Stage 7 enrols its pilot learner with the course's **manual** enrolment method. Every organisation reaches a course through **cohort sync** (002). In report builder, `enrol:plugin` is a column, a condition and a filter (`enrol/classes/reportbuilder/local/entities/enrol.php`):
- organisation reports and the programme report have the fixed condition `enrol:plugin = cohort`;
- a **pilot report** has `enrol:plugin = manual`, and its audience is the site team.

So pilot numbers never reach delivery figures (FR-012).

A learner enrolled both ways appears once in each report, not twice in one. The datasource gives one row per enrolment, and the condition picks one.

> **Amended by spec 002 R10 (Doug, confirmed 2026-10-02; a0389bc, PR #92; this note 2026-10-05).** Managers may enrol their own learners, and they do it through a separate `enrol_self` instance per course, the organisation-enrolment instance, which learners cannot use themselves (`customint6 = 0`, marker `customchar1 = ltct:orgenrol`). So delivery is no longer cohort sync alone. The organisation and programme reports' condition is `enrol:plugin` **not equal to** `manual` (`moodle/site/reports.yaml` `progress` and `programme`; `SCOPE_CONDITIONS` in `scripts/site_config.py`), because report builder's select condition holds one value (`filters\select` `EQUAL_TO 1`, `NOT_EQUAL_TO 2`) and cannot say "cohort or self". The pilots report keeps `enrol:plugin = manual`. If `enrol_manual` were disabled the not-equal condition would produce no SQL and the report would widen (MDL-84213), so `apply` and `drift` refuse that, as for every scope condition. The coverage datasource counts both delivery methods (R15's amendment). The two bullets above are kept as written for the record.

**Rationale**: Enrolment method is recorded by Moodle for every enrolment, from the moment it is made, and needs nothing new on the server. `process/stages/07-pilot.md` gains one line saying how the pilot learner is enrolled.

**Alternatives considered**:
- A "pilots" cohort. That would be another membership for the site team to keep, and a person could be a pilot in one course and a delivery learner in another.
- Splitting pilot and delivery by the course's category. The same course serves both, so that cannot work.
- A completion date before the stage-8 date, which the platform does not know.

**Confirmed in source (T001): condition values, and how a scoping condition can fail open.**
- `base::set_condition_values(array $values): bool` (`reportbuilder/classes/local/report/base.php:614`) replaces `report.conditiondata` with `json_encode($values)`; it does not merge. `get_condition_values()` (:626) returns `(array) json_decode(conditiondata)`. Keys are `<entity:name>_operator` and `<entity:name>_value` (`local/filters/text.php:87–117`, `select.php:95–125`).
- `base_report_table` (`table/base_report_table.php:81–89`) applies every active condition through `get_active_conditions(false)`, so a condition hidden from a viewer still applies. But a condition whose SQL comes back `''` is skipped without a word.
- `select::get_sql_filter()` returns `['', []]` when the operator is "any value" or when the value is not a key of the filter's current options (MDL-84213). All three scoping conditions are selects:
  - `enrol:plugin` is keyed by the **enabled** enrol plugin names, `enrol_get_plugins(true)` (`enrol/classes/reportbuilder/local/entities/enrol.php:171–183`). If `enrol_cohort` is disabled, the condition vanishes.
  - `role:name` is keyed by **role id**, `role_get_names(null, ROLENAME_ORIGINAL, true)` on `{role}.id` (`admin/roles/classes/reportbuilder/local/entities/role.php:166–176`). The stored value must be the student role's id, resolved by shortname at apply. The string `student` would be dropped.
  - `user:profilefield_ltct_org`, a menu field, is keyed by the raw option string (`reportbuilder/classes/local/helpers/user_profile_fields.php:182–218`; `user/profile/field/menu/field.class.php:64`). An organisation key removed from the field's options silently unscopes that organisation's report.
- In each case the report then shows every participant the other conditions allow. So `apply` and `drift` prove that each scoping condition produces SQL: build the condition's filter instance and check `get_sql_filter($values)[0] !== ''`. If it does not, that report fails hard.

> **Amended 2026-10-05.** Only two of the three scoping conditions are selects now. The organisation is `cohort:idnumber` equal to `ltct:org:<key>`, a **text** condition (`filters\text` `IS_EQUAL_TO 3`; spec 016 R11, d395494, PR #84), which produces SQL for any value and matches nobody when the cohort does not exist, so it fails closed. `enrol:plugin` is not equal to `manual` (spec 002 R10, above), so it vanishes if `enrol_manual` is disabled, not `enrol_cohort`. The guard in `reports.php` `resolve()` still builds every declared condition and blocks the report on empty SQL (`empty_sql_reason()` names a disabled enrol plugin).

## R11. Competencies and target level reach Moodle as locked course fields

**Decision**: A course's competencies and target level need to show beside the course: in the programme report, on the course, and in spec 007's grouping of My courses. In the participants datasource, the course entity includes **course custom fields** as columns, conditions and filters. Course tags are joined only in the courses datasource, which has no completion entity. So the publisher writes two course custom fields, declared in a new `moodle/site/course-fields.yaml`. The table with a row per competency is a separate design, R15.
- `ltct_competencies`: the course's frontmatter `competencies`, each name verbatim and in brackets, for example `[Translation Tools] [Paratext]`. Brackets matter because "Translation" is contained in "Translation Tools" and "Linguistics" in "Computational and Corpus Linguistics". A "contains `[Translation]`" filter would otherwise match both. `validate` fails if any name contains `[` or `]`.
- `ltct_target_level`: the frontmatter `target_outcome_level`, verbatim, for example `2 - With Assistance`.

Both fields are text, locked and visible to everyone. Their display names come from FR-010: "Competencies this course aims at" and "Level this course aims at".

**Creating the fields**: The applier calls `core_course\customfield\course_handler::create()`, `create_category()` and `save_field_configuration()` (`customfield/classes/handler.php`). The field category is found by name, as 002's profile field category is, because a customfield category has no idnumber. The name lookup keeps only categories with `component = core_course` and `area = course`, because the handler also returns enabled shared categories, and a shared one with the same name must not be adopted. Fields are found by `shortname`.

**Writing the values**: The publisher sends `customfields: [{shortname, value}]` in `core_course_create_courses` and `core_course_update_courses`. The update writes through `data_controller`, but only for fields the caller may edit. A locked field needs `moodle/course:changelockedcustomfields`, which `ltcpublisher` gains. Both web services **silently drop** a field that is unknown or not editable, with no warning and no error. So the publisher reads the values back with `core_course_get_courses_by_field` and compares `valueraw`.

**Not for counting**: A text field cannot give one row per competency, because report builder cannot split a multi-valued field into rows. An earlier draft built a "one competency at a time" report on this field. The maintainer rejected it on 2026-10-02 (plan "Decisions on the plan's limits", #4), and R15 replaces it.

**Rationale**: The frontmatter stays the source of truth, and Moodle holds a copy the publisher refreshes. A custom field is only course metadata, so it adds nothing to the disclosure boundary. `block_myoverview` can also group by a course custom field, which spec 006 or 007 may use.

**Alternatives considered**:
- Core competencies (`tool_lp`) with course competencies. They invite "competency achieved" records, which Principle V forbids here (R15).
- Course tags (above).

## R12. Scheduled reports are declared, one per organisation

**Decision**: Each organisation report has one declared schedule:
- weekly (`RECURRENCE_WEEKLY = 3`);
- in format `excel`, the enabled `dataformat_excel`;
- sent to the report's own audience, the managers cohort;
- with `userviewas = REPORT_VIEWAS_RECIPIENT (-1)`, so `message::execute()` runs as each recipient through `cron::setup_user()`. A recipient therefore never receives more than they could open themselves;
- with `reportempty = REPORT_EMPTY_DONT_SEND (2)`, so nothing is sent when there are no rows, which covers a manager with no learners yet. (`0` would send an empty attachment, and is the default.)

The schedule's owner, `usercreated`, is the admin account `apply` runs as.

**What "subscribe" means**: Creating a schedule needs edit rights on the report, `moodle/reportbuilder:edit` or `editall`, which an organisation manager does not have. So a manager does not subscribe themselves. They are subscribed by being a manager of their organisation. Opting out is done by the site team, with a per-person audience exclusion that core does not offer, or by the manager filtering the email.

This is weaker than US4's "has subscribed". It is recorded as a decision for SC-003's real managers to test, and for the maintainer to accept. Per-manager opt-in would need a second cohort per organisation, `:subscribers`, which adds another membership for the site team to keep. That is the named fallback if managers ask for it. The maintainer has not yet confirmed this (plan "Decisions on the plan's limits", #2).

**Burden (constitution X)**: Scheduled email depends on outgoing mail. That is spec 001's baseline on the build host and spec 015's on production. The operator who would notice a mail failure is undecided (015). This plan does not claim scheduled delivery is covered in production.

## R15. The per-competency table is a `local_ltuse` report builder datasource

**Decision**: The site team gets one report with a row for every framework competency. It is built on a `local_ltuse` report builder datasource, `local_ltuse\reportbuilder\datasource\competency_coverage`. The datasource's main table is the competency list itself. So a competency that no course declares is still a row, and its counts are 0.

The plan uses three pieces, all rebuilt from the repo:
- **The competency list**: table `local_ltuse_competency` (name, category, sortorder, retired). `site_config.py apply` fills it from the repo-root `competencies.yaml`. There is no copy under `moodle/site/`. The `Meta` category holds only `Uncategorized` and is left out. That is the rule `site_config.py` already applies to expertise checkboxes (`META_CATEGORY`). So the table has 42 rows.
- **The course map**: table `local_ltuse_course_comp` (courseid, competencyid). The publisher writes it on every publish from the README frontmatter `competencies:`, through a new web service, `local_ltuse_set_course_competencies`. The write is one-way (Principle I).
- **The report**: one template in `reports.yaml`, key `competency-coverage`, with source `competency_coverage`. Its audience is `systemrole` with `manager`. It has no conditions.

**The counts**: Each count column is one correlated subquery, added with `column::add_field()`. That method's docblock allows "a complex sub-query that returns only one field", and it takes params. Such a field must pass an explicit alias, and every param name must come from `database::generate_param_name()` (see below). A subquery returns 0 when nothing matches, so no row is ever dropped. The columns are:
- **Courses that aim at it**: mapped courses that exist and whose `idnumber` starts with `ltct:`. This includes a course still in pilot, because pilot and delivery are the same Moodle course (R10).
- **Of which in delivery**: those courses that have an enabled cohort-sync instance (`e.enrol = 'cohort'`, `e.status = 0`) whose role is `student`.
- **Delivery enrolments**: active user enrolments (`ue.status = 0`) on those instances, users not deleted. This counts enrolments, not people. One learner in two courses aiming at X counts twice.
- **Delivery learners**: the same, counted by distinct user.
- **Delivery course completions**: `course_completions` rows with `timecompleted` set, in mapped courses, where the user holds a cohort/student enrolment in that course in any status. A moved learner's completion still counts, once.

> **Amended by spec 002 R10 (a0389bc, PR #92; this note 2026-10-05).** "Cohort-sync instance" above now reads "delivery instance": an instance with the student role that is either cohort sync (`e.enrol = 'cohort'`) or the course's organisation-enrolment instance (`e.enrol = 'self'` and `e.customchar1 = 'ltct:orgenrol'`), through which a manager enrols their own learners (`coverage.php` docblock and `delivery_instance()`, `moodle/local_ltuse/classes/reportbuilder/local/entities/coverage.php`). It must be enabled for "Of which in delivery", the enrolments and the learners; the completions count a delivery enrolment on an instance in any status, as before (`delivery_instance($e, false)`). So "Of which in delivery" also counts a course whose only enabled delivery instance is the organisation-enrolment one, and the enrolment, learner and completion counts include learners a manager enrolled through the organisation-enrolment instance. Any other self-enrolment and every manual enrolment are still left out.

The role is looked up as `roleid IN (SELECT id FROM {role} WHERE shortname = 'student')`, never by id. That excludes each organisation's managers cohort, which 002 R2 cohort-syncs as `orgmanager`. The manual enrolment method is never counted, so pilots stay out of delivery figures (FR-012, R10). These filters are in our SQL, not in report conditions, so nobody can remove them by editing the report. A report condition on a joined table would also drop exactly the zero rows the table is for.

**What it does not show**: no user, course or enrolment entity is on the datasource, so a report built on it can only show counts per competency. It uses no `tool_lp` or `core_competency` data, and no column shows a level (Principle V).

**Lifecycle**: `apply` inserts a declared competency that is missing. It updates a changed category or sortorder. A live competency that is no longer declared is reported `extra` and kept, but marked `retired`, so it leaves the table and keeps its map rows. A renamed competency is therefore a new row, and each course moves to it on its next publish. The web service refuses a name that is not in the list and leaves the map unchanged. So apply runs before a publish that uses a new competency. A deleted course drops out of every count, because each subquery joins `{course}`. Its stale map rows are harmless and are not cleaned.

**R11's course fields stay**: `ltct_competencies` and `ltct_target_level` are still written. They serve per-course display, the programme report and spec 007's grouping. They are not used for this table.

**Rationale**: Core cannot build this table. The participants datasource has course fields, enrolments and completions, but report builder cannot split a multi-valued field into rows. The courses datasource has tags but no completion entity. Core's `core_competency\reportbuilder\datasource\competencies` exists on 5.2. It joins framework, competency, user competency and user, plus context and cohort entities (`competency/classes/reportbuilder/datasource/competencies.php:51–97`), and its measure is the learner rating that Principle V forbids. Report builder's documented extension point is a datasource in our own plugin. `manager::get_report_datasources()` finds it by namespace (`reportbuilder\datasource`), and nothing has to be registered.

**Principle XI**: This is our code on a supported extension point (form 3). It writes only to its own two tables. The datasource reads `{course}` (id, idnumber), `{enrol}` (courseid, enrol, status, roleid), `{user_enrolments}` (enrolid, userid, status), `{user}` (id, deleted), `{role}` (shortname) and `{course_completions}` (course, userid, timecompleted) in SQL. Each read is read-only and aggregate-only, uses the same join shapes as core's participants datasource, and is listed in the plugin README with its reason. Column identifiers such as `coverage:completions` are stored in saved reports. They are frozen once released. Every Moodle branch re-checks the datasource and entity base classes against `reportbuilder/UPGRADING.md`.
