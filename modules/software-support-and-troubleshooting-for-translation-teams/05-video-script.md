# Video script

Companion recording script for the course **Software Support and Troubleshooting for
Translation Teams**. This is the overview video: it shows the learner the shape of the
five-step troubleshooting framework and the communication habits that go with it, before
they work through the lesson, the scenario bank and the quiz. It is **not** a read-aloud of
the lesson. The lesson carries the full question lists, issue categories and toolkit; the
video's job is to make the framework feel familiar and to change the learner's first
reaction to a panicked message. Recording happens outside this repo, and uploading to
Cypher for Business is a separate human step.

This course is tool-agnostic and has no hands-on software exercise, so the video is mostly
**slides with voiceover**, plus one optional screen-share moment (Segment 3). It builds on
an earlier recording of this course whose captions are in `video_captions.vtt`. Where those
captions agree with the lesson, this script keeps their wording and tone. Where they don't,
it follows the lesson.

**Estimated runtime:** 9–10 minutes.
**Companion lesson file(s):** `01-software-support-and-troubleshooting.md` (the course's
single lesson and its overview). The close hands off to `02-scenario-bank.md`.

## Overview / cold open

> Runtime target: ~60 seconds. Open on the message, not a title slide.

**On-screen:** A plain chat/email mock-up holding the lesson's Connect message, word for
word:

*"Help! Nothing is working. I was translating yesterday and everything was fine, but today
when I opened the program, my work isn't showing up. I have a deadline tomorrow and I'm
panicking. What do I do?"*

**Voiceover:** "We've all been there. Either you're the one sending a frantic message for
tech help, or you're the one receiving it. And for a translator, when a piece of software
breaks, it isn't a small annoyance. It's a direct threat to a deadline. So imagine this
lands in your inbox. You can feel the panic coming through the screen. So what's your gut
reaction? Do you start firing back possible fixes right away? Or, honestly, do you feel a
bit of that panic yourself, worried you won't know the answer? That first instinct is what
this course is about. Being good at support isn't about being a genius with every answer
memorised. It's about having a calm, methodical system that lets you walk into that chaos
and bring some order to it."

## Script

### Segment 1: What these messages really are (companion to lesson Section 1)

> ~1 minute. Framing. Keep it quick.

| On-screen | Voiceover / talking points |
| --- | --- |
| Slide: a range from **"I can't find the button"** to **"the synchronization is corrupted"**. | "Support requests for translation teams run from simple misunderstandings, like 'I can't find the button', to real technical problems, like corrupted synchronisation. And you won't know everything about every tool. That's okay." |
| Slide, key point: **Effective support = knowing how to figure out what's wrong, and where to find help.** | "Effective support isn't about knowing every answer straight away. It's about knowing how to work out systematically what's wrong, and where to find help when you need it." |
| Slide with three icons: **Technical troubleshooting**, **Translator workflows and context**, **Clear, empathetic communication**. | "Your role combines three things. You need the technical skills to work out the problem. You need to understand how translators actually work. And you need the communication skills to keep a stressed person calm and focused. So how do you juggle all of that? You use a framework. It isn't a boring checklist. It's what brings structure to the mess and gets you to a solution without wasting time." |

### Segment 2: The roadmap (companion to lesson Section 2, overview)

> ~30 seconds. Show all five steps once. Leave this slide up long enough to read.

| On-screen | Voiceover / talking points |
| --- | --- |
| Slide, five numbered steps in a row: **1. Clarify the Problem → 2. Understand the Context → 3. Reproduce the Problem → 4. Test Systematically → 5. Know When to Escalate.** | "Here's your roadmap. Five steps you can apply to almost any problem you come across. Clarify the problem. Understand the context. Reproduce the problem. Test systematically. Know when to escalate. Follow them in this order and you stop reacting to the panic and start solving the actual problem. Let's walk through them." |

### Segment 3: Clarify the Problem (companion to framework step 1)

> ~1.5 minutes. The heart of the video. The Send/Receive example makes the point, so don't rush it.

| On-screen | Voiceover / talking points |
| --- | --- |
| Slide: **"Nothing works." "It's broken."** with the label *= a starting point, not a problem description.* | "Everything starts with that panicked message. 'It's broken' is only the signal flare. Your first job, before anything else, is to get past the emotion and find out what's really going on." |
| Slide: the five clarifying questions, one at a time. **What were you trying to do? / What happened instead? / When did you first notice this? / Has anything changed recently? / Can you show me exactly what you're seeing?** | "So you ask. What were you trying to do? What happened instead? When did you first notice it, since the timeline helps point to a cause. Has anything changed recently, like an update, new files, or a different location? And can you show me exactly what you're seeing, whether that's a screenshot, the error message, or what's on screen." |
| Slide: **"Send/Receive isn't working."** Then reveal six possible meanings, each with its likely direction: greyed-out button (permissions) / starts but never finishes (network or server) / shows an error (a specific error to diagnose) / completes but *their* changes don't appear (synchronisation) / completes but *another user's* changes don't appear (synchronisation, or the other user hasn't run Send/Receive yet) / can't find where to click (unfamiliar interface). *Optional:* a brief screen-share of a Send/Receive button on a demo project. See the presenter notes. | "Here's why questions matter so much. A translator tells you 'Send/Receive isn't working.' What does 'isn't working' actually mean? The button might be greyed out, which points to permissions. It might start and never finish, which points to the network or the server. It might show an error message. It might finish, but their changes don't show up. Or it finishes, but a teammate's changes don't show up, maybe because the teammate hasn't run Send/Receive yet. Or they just can't find where to click. Each of those has a different cause and a different fix. Your questions are what turn a vague complaint into something you can actually fix." |

### Segment 4: Understand the Context, then Reproduce (companion to framework steps 2 and 3)

> ~1.5 minutes. Two steps, one segment. Step 2 is where new consultants most often fall short, so give it its full time.

| On-screen | Voiceover / talking points |
| --- | --- |
| Slide, four context headings: **Project structure / Collaboration setup / Work environment / Recent changes.** | "Once you know the symptom, look at the context around it. Is this a team project or individual files? Brand new, or running for years? Are several people working on the same data, and how are they sharing it? Are they in the field with limited connectivity, or in an office with stable internet? On their own device or a shared computer? And what just changed? A new operating system, a new software version, someone new on the team?" |
| Same slide, caption added: **Context tells you what's normal, and what isn't.** | "You can't tell whether something is abnormal until you know what normal looks like for this team. Context helps you ask the right questions and get to the likely causes faster." |
| Slide: **See it for yourself.** Icons for screen-share and for working side by side. | "Step three: whenever you can, see the problem for yourself, or have the translator show you exactly what's happening. Watching lets you check what's actually occurring against what they think is happening. You'll notice details they wouldn't think to mention, and you can test possible fixes right there." |
| Slide: **"It's not working" → "I'm clicking the wrong button."** | "Sometimes 'it's not working' turns out to be 'I'm clicking the wrong button' or 'I'm looking in the wrong place.' Screen-sharing shows you that straight away. Talking about it might never have got you there." |

### Segment 5: Test Systematically (companion to framework step 4)

> ~1 minute. Keep the file example as a simple ladder on screen.

| On-screen | Voiceover / talking points |
| --- | --- |
| Slide, four rules: **Simplest, most common causes first / Change one thing at a time / Write down what you tried / Understand *why* the fix worked.** | "Now test, and do it methodically, not by trying things at random. Start with the simplest, most common causes. Change one thing at a time so you know what worked. Write down what you tried and what happened. And when something fixes it, make sure you understand why." |
| Slide, a four-rung ladder titled **"The file won't open."** 1. Can they open *other* files? 2. Can someone else open *this* file? 3. Does it open on a different computer? 4. Is there a backup to try? | "Say a file won't open. Can they open other files? That tells you whether it's this file or all files. Can someone else open this one? That's the file versus their setup. Does it open on a different computer? That's their device versus the file. And is there a backup they can try, to work around a corrupted file? Every question cuts the possibilities down to something you can manage." |

### Segment 6: Know When to Escalate (companion to framework step 5)

> ~1–1.5 minutes. The attitude matters more than the list. Let the "not a failure" line land.

| On-screen | Voiceover / talking points |
| --- | --- |
| Slide, five signs it's time to escalate: **You've tried the usual fixes and you're making no progress / You suspect data corruption / The fix needs administrator rights you don't have / The problem is beyond what you know / The translator's deadline is close and you're still investigating.** | "You won't solve every problem straight away, so part of the skill is spotting the red flags. If you've tried the usual fixes and you're getting nowhere, it's time. If you even suspect data corruption, it's time. If the fix needs admin rights you don't have, or it's just beyond what you know, it's time to escalate. And if the translator's deadline is close and you're still investigating, that's a good time to bring in reinforcements too." |
| Slide, four next steps: **Consult someone more experienced / Contact software vendor support / Restore from backup and move forward / Find a workaround rather than a complete fix.** | "When you see one of those signs, pick the route that fits. Bring in someone more experienced. Contact the software vendor's support. Restore from backup and move forward. Or find a workaround so the translator can keep working, even without a complete fix yet." |
| Slide: **Escalating is not failing.** | "And let this one sink in: knowing your limits and being willing to ask for help is a strength, not a weakness. Escalating isn't a sign you failed. It's a professional decision that protects the translator and their work." |

### Segment 7: How you talk while you work (companion to lesson Section 3)

> ~1.5 minutes. Put each phrase on screen as it's spoken. These are the lines learners will reuse.

| On-screen | Voiceover / talking points |
| --- | --- |
| Slide: **"I can hear this is really frustrating. Let's figure out what's happening together."** | "A good framework is only half of it. How you communicate while you work through the steps makes all the difference, especially with a deadline hanging over someone. Think about a sentence like this. You've acknowledged their stress, and you've made it a partnership: let's figure this out together. You're not just tech support any more. You're an ally, and that brings the tension right down." |
| Slide: **"I'm going to ask you some questions to help me understand exactly what's going on. Then we'll work through this systematically."** | "Tell them what you're doing. When they know why you're asking all these questions, the questions stop feeling like a delay." |
| Slide: **"I haven't seen this exact error before, but let me check a few things with you."** | "Be honest about what you know and what you don't. Pretending to know, or offering false reassurance, will get you into trouble. 'I haven't seen this one before, but let me check a few things with you' is far more reassuring than faking it." |
| Slide: **"I want to investigate this properly rather than guess. Can I get back to you in two hours with a solution or at least a clearer picture of what's happening?"** | "Manage expectations. If you need time to research, say so, and say when you'll get back to them. That's much better than going quiet, because silence is where a user's anxiety really starts to spiral." |
| Slide: a simple three-column table headed **Problem / Symptoms / Solution**. | "And when you solve something, write it down. Problem, symptoms, solution. It helps you next time, and over time it becomes a resource for the whole team." |

### Segment 8: Patterns you'll see, and your toolkit (companion to lesson Sections 4 and 5)

> ~45 seconds. A preview only. Do not walk every bullet. The lesson has the detail.

| On-screen | Voiceover / talking points |
| --- | --- |
| Slide, five category tiles: **Synchronization / Missing work or data / Installation & compatibility / Performance / User interface confusion.** | "Every situation is different, but some patterns come up again and again. Synchronisation problems. Work that seems to be missing. Installation and compatibility trouble after an update. Performance problems on big projects. And someone who simply can't find a feature, often because the interface changed. The lesson goes through what usually causes each one and where to start looking. Take the time to read it. Knowing these patterns makes the first questions much easier to choose." |
| Slide, four toolkit headings: **Knowledge resources / Diagnostic tools / Communication tools / Personal habits.** | "The lesson ends by helping you build a support toolkit: where to find answers, tools for seeing what the translator sees, templates for questions and progress updates, and habits like keeping notes on what you've solved." |

## Call to action / close

> ~45 seconds.

**On-screen:** Return to the cold-open message. Then a closing slide showing the new loop,
**Pause → Ask → Test one thing at a time → Communicate throughout**, and below it:
**Lesson → Scenario bank → Submit to your mentor → Quiz.**

**Voiceover:** "So let's tie it together. The panicked message comes in. Your old instinct
might be to jump in with answers. Your new instinct is to pause and ask questions before you
diagnose. You test one thing at a time so you know what worked. And you communicate the
whole way through. That loop is what separates good troubleshooters from great ones. Now
work through the lesson. When you reach the Challenge, you'll see a message just like this
one. Write down the first three questions you'd ask. Then go on to the scenario bank, which
has two more real-world situations, and submit your written answers to your mentor for
feedback before you take the quiz. The next time one of these messages lands in your inbox,
you'll have a system. The only question left is: what's the first clarifying question
you're going to ask?"

## Notes for the presenter

- **This is an orientation, not the lesson read aloud.** The lesson has the complete
  question lists, issue categories and toolkit. If the recording runs long, cut Segment 8
  first, then shorten Segment 4. Don't cut the Send/Receive example (Segment 3) or the
  communication phrases (Segment 7).
- **Tool-agnostic course.** Apart from "Send/Receive", which comes from the lesson's own
  example, don't name a specific translation program on camera or imply the steps belong to
  one tool. The design doc keeps this course tool-agnostic on purpose (SME decision, Q5).
- **Optional screen-share in Segment 3.** If you show a Send/Receive button, use a demo or
  practice project. Don't show real project text, names or server details. This repo and
  the published video are public. If there's no suitable demo project, stay on the slide.
- **No language data on screen.** The lesson has no local-language examples and neither
  does this script. Don't add a real error screenshot or any project text in a language
  you don't speak to "illustrate" a point. If a future edit needs one, it has to come from
  the project team or the author, with permission, and shown without any gloss or comment
  on what it says.
- **Keep the cold-open message word for word.** It is the lesson's Connect prompt, and
  learners will see it again when they open the lesson.
- **Terms to put on screen:** the five step names (Segment 2, and ideally as a small
  progress strip during Segments 3–6), and **Send/Receive** the first time it's said, so
  learners who haven't met the feature yet can see it's a named action.
- **Don't promise specific fixes.** The Send/Receive causes in Segment 3 are the lesson's
  "likely direction" for each symptom, not guaranteed diagnoses. Say "points to", not
  "is caused by".
- **Escalation signs (Segment 6).** The five signs come from the earlier recording
  (`video_captions.vtt`) and now match the lesson's "Know When to Escalate" list word for
  word. That list is flagged for SME confirmation at stage 5. If the SME changes it, update
  this slide and voiceover to match the lesson before recording.
- **Pacing:** Segment 2's roadmap slide and the Segment 7 phrases each need enough screen
  time to read. Don't talk over a slide change.
