    Video script¶

    Companion recording script for the course Supporting Scripture Pre-publishing Checks. This is an orientation/overview video: a walkthrough of the shape of the five check-area lessons and the recurring "false-clean" thread that runs through all of them, so a learner has the map in their head before working the lessons in detail. It is not a full read-aloud of the lessons — the click-by-click tool work, the Challenge exercises, and the mentor-reviewed scenario bank all happen outside this video. The recording happens outside this repo; uploading it (to Vimeo or Google Drive, then linking it from lesson 1) is a separate human step.

    Estimated runtime: 16-18 minutes (overview companion to five 35-85 minute lessons plus the mentor-reviewed scenario bank). Companion lesson file(s): 01-supporting-the-final-turn.md through 05-glossary-linking-and-layout.md — one orientation segment per lesson, plus a closing segment on the scenario bank (06-scenario-bank.md).

    Overview / cold open¶

    Runtime target: ~60-90 seconds. Open on a live screen recording, not a title slide.

    On-screen: Live screen recording of a Paratext Project Plan ("Assignments and Progress" view) showing a Stage 6 task with a clean "No issues" status. Presenter clicks into the underlying wordlist or Basic Checks results for that same task and reveals either a struck-through denied error or a wordlist blanket-marked Correct sitting underneath the clean status.

    PRESENTER NOTE — confirm before recording: verify which specific screenshot/live project state you'll use here; 04-formatting-and-references.md (denied error, strikethrough + View > Denied messages) and 02-wordlist-and-biblical-terms.md (blanket-approved wordlist) both have field-confirmed examples — pick one live project state you can reliably reproduce on camera rather than staging it from a screenshot.

    Voiceover: "A team tells you they already did a check, and the Project Plan agrees: no issues. But open what's underneath, and here's a wordlist of thousands of words, every single one marked Correct without anyone actually looking. Or here's an error a team denied because they didn't understand it, hidden because one View menu option is switched off. The check status only reflects what the check machinery can see — it doesn't see a human override underneath it. That gap, between a clean status and a genuinely reviewed one, is the thread running through every lesson in this course. In the next few minutes I'll walk you through where it shows up in each check area, then you'll build the skill of spotting it yourself."

    Script¶

    Segment 1 — The spiral, the final turn, and your role (companion to Lesson 1)¶

    ~2.5 minutes. Concept framing — no tool demo needed here beyond the Project Plan.

    On-screen Voiceover / talking points
    Simple slide: a spiral diagram with six labeled turns, the sixth turn highlighted and labeled "pre-publishing — the final turn." "A translation project doesn't move through its checks in one straight pass — think of it as a spiral. The same check areas come back around more than once, at increasing levels of polish. By the time a project reaches Stage 6, pre-publishing, whatever was missed, introduced, or left unresolved at any earlier turn is still sitting in the text — because this pass is what the typesetter treats as final."
    Cut to a live screen recording of the Project Plan ("Assignments and Progress" view), showing a per-task status like "3 issues" or "No issues," and the presenter clicking to re-run one check directly from that view. "Your starting point is the Project Plan — you already know it. It's live, it's current, and you can rerun any individual check straight from here. A 'No issues' status only reflects what the check machinery can see, though. It doesn't undo a denied error or a blanket-approved status. Those are human overrides, and an automatic recheck doesn't catch them."
    Slide: three labeled buckets — Yours (tooling/process), The team's (translation decision), Escalate (LT mentor / Translation Consultant). "Every issue you find sorts into one of three buckets. Yours to diagnose and coach through directly. The team's own translation call — you confirm the check ran and was reviewed, you don't adjudicate the language. Or an escalation — a tooling problem beyond you goes to an LT mentor; a content question goes to a Translation Consultant. And in every bucket, the rule is the same: you diagnose and coach, the translator makes the actual correction at their own keyboard."

    Segment 2 — Wordlist and Biblical Terms (companion to Lesson 2)¶

    ~3.5 minutes. Two related tools; show the false-clean pattern once, then Biblical Terms' three patterns briefly.

    On-screen Voiceover / talking points
    Live screen recording (or the module's captured image, assets/ss-02-blank-bt-row.png) of a Biblical Terms row at its default state: orange highlight, "Double click to enter rendering(s) from project text." "Every term in the Biblical Terms tool starts blank, highlighted like this — that's not a bug, it's the tool's normal starting state. The risk isn't the blank row itself, it's a team presenting a partially-filled list as done. You don't catch that by eyeballing the list — you check the Found column, row by row: a filled count like 2 of 2, versus a row still sitting unfilled."
    Cut to the module's assets/ss-02-term-only-2-renderings-used.png — a term showing three candidate renderings but a Found count of only 2/11. "A second pattern: renderings pile up over time. An old, possibly-wrong rendering gets left in place after a correct one is added, and now it's unclear which one the team actually intends. The Found count tells you which renderings are actually still live in the text."
    Brief live recording: stepping through a term's occurrences with the down arrow, a rendering that repeats the verse's first word standing out against real translations. "A third, less common pattern — a rendering that's just the verse's first word, repeated. The likely cause, per a support.bible reply, is running Guess Renderings before the project had enough translated data — an automated side effect, not something a translator would notice happening. Step through a term's occurrences with the down arrow and it becomes visually obvious."
    Slide: "There is no technical way to detect a blanket-approved wordlist." Then a live recording of resetting a full wordlist to Undecided. "And the wordlist itself: Paratext genuinely cannot tell you whether a wordlist was reviewed one entry at a time or swept up in one blanket approval. So you ask the team directly — and if there's any doubt, you reset the whole list to Undecided and review it together from a clean slate. That loses nothing; only the approval status resets."

    Segment 3 — Parallel passages and numbers/measures (companion to Lesson 3)¶

    ~3 minutes. Emphasize the "confirm process, don't judge language" reframe.

    On-screen Voiceover / talking points
    Slide: "Your job here is process and routing — not judging meaning." "You typically don't speak the language a team translates into. So in this lesson, your role is deliberately narrower: confirm the check ran, confirm the team reviewed what it found, and hand judgment about wording back to them."
    Live recording (or assets/ss-03-pp-changed-text.png) of the Parallel Passages tool, Status column showing a green checkmark on one row and a red "?" on another. "The Parallel Passages tool puts related passages side by side, and shades where they match, but it doesn't judge or flag inconsistencies for you. What it does track is review status: a checkmark means reviewed and approved, a red question mark means the verse changed since it was last approved and needs another look. Your job is to open this tool and check for red question marks yourself, not take the team's word that a pass already happened."
    Slide: "No more harmonized than the original texts." "Watch for over-harmonising — making parallel passages match more closely than the original texts do. Different biblical authors may relate a story differently. That call belongs to the team."
    Cut to assets/ss-02-bt-choose-list.png or equivalent — the Open Biblical Terms List dialog showing Numbers as a separate entry. "Numbers and measures checking is mid-change right now — a new consolidated check covering numbers, weights, and measures together is expected to replace the older, separate Numbers check, but not every team's Paratext version has it yet. Your skill here doesn't depend on which one ships first: confirm what a specific team's version actually has, run whichever check is available against their own already-agreed, documented approach, and route any gap back to them."

    Segment 4 — Formatting, structural-first order, and the Punctuation Inventory (companion to Lesson 4)¶

    ~4 minutes. This is the longest lesson (85 min); keep the demo tight and lean on the before/after image.

    On-screen Voiceover / talking points
    Slide listing the eight-step structural-first order: Chapter/Verse Numbers → marker pairs → ghost markers → long/short verses → headings → book titles → references → footnotes. "Formatting errors cascade, so you work structural-first. Chapter and Verse Numbers come first, always — every other check on this list reports its results by quoting a chapter and verse location, and those locations can't be trusted if the numbering itself has errors."
    The module's before/after pair (assets/ss-04-p-marker-in-place.png and assets/ss-04-p-marker-missing.png) — a section heading with its \p marker correctly in place, versus one where it's missing and verse text has been swallowed into the heading style. "Here's why order matters. One missing paragraph marker after a section heading, and everything up to the next paragraph marker gets swallowed into the heading style — verse numbers included. Fix that one marker, and a whole cluster of downstream-looking symptoms disappears with it. This before/after pair is worth remembering: it's the clearest example in this course of one small error cascading into many."
    Live recording (or assets/ss-04-denied-error-strikethrough.png and assets/ss-04-denied-error-not-shown.png) of a denied error shown with strikethrough, then the same list with View > Denied messages switched off. "Basic Checks results have a genuine accept/deny mechanism — unlike the wordlist's Correct/Incorrect/Undecided. A denied error, when visible, shows struck through. But whether you see it at all depends on one View menu setting, Denied messages — switch it off, and denied items vanish from the list entirely. A short, clean-looking list may just have its denied items out of view."
    Live recording of Tools > Checking Inventories > Punctuation Inventory, opening its Inventory menu and selecting "Show sequences," then a separate look at the Unmatched Pairs of Punctuation inventory. "Two more inventories worth knowing before a project reaches a typesetter. The Punctuation Inventory's 'Show sequences' option relabels the Run Basic Checks punctuation box to 'Punctuation (sequences)' and catches multi-character combinations — without it, that same box silently only checks single characters. Unmatched Pairs of Punctuation is a separate, complementary inventory that catches single unmatched brackets and parentheses directly. Neither replaces the other, and both are easy to assume are 'already handled' on a project that's far along — confirm they were genuinely reviewed."

    Segment 5 — Glossary linking, layout, and the final read-through (companion to Lesson 5)¶

    ~3.5 minutes. Three sub-areas; keep each brief.

    On-screen Voiceover / talking points
    Live recording (or assets/ss-05-find-with-markup.png) of a Paratext Find search for a glossary term, showing one plain occurrence and one wrapped in \w...\w* markup. "Glossary over-linking — every occurrence marked instead of just the first per section — doesn't leave a durable report to check later; the linking operation's own report is transient. Use Find instead: search the term, and read the markup on each result. If every occurrence is wrapped, that's over-linked; if only the first per section is, the scope is right."
    Slide: "Layout follows reader expectation, not word length." "A team may assume single-column layout because their language has long words — but if the community's existing Bibles, in a language of wider communication, are conventionally printed in two columns, that reader expectation is the baseline to match, not the word-length problem."
    Live recording (or assets/ss-05-wordlist-hyphenation.png) of the Wordlist's Show hyphenation view — a grey tick, a click, the tick turning green; then a shift-click batch-approval. "Hyphenation isn't hand-built — Paratext's Wordlist auto-generates it. Turn on Show hyphenation in its View menu, and each word carries a tick: grey means guessed, unreviewed; green means approved. But where a word may break is the team's call, not yours. Draft breaks from the syllable rules in their orthography statement — or, if there isn't one, enter the breaks they propose — have the team confirm each break, then approve the confirmed ones, singly or in a batch. Do this before the files go to print — PTXprint's draft PDF will use unapproved guesses too."
    Live recording (or the module's PTXprint spread images) of a draft-PDF spread showing an awkward heading break and an underfilled column. "Last stop: the draft-PDF read-through in PTXprint. Watch for spreads, orphan words, footnote shifts, awkward heading placement, and underfilled pages — and triage what you find. Some of it's yours to fix, some is the team's call, and true typesetting composition belongs to the typesetter, not you."

    Segment 6 — Where this goes next (companion to the scenario bank)¶

    ~1.5 minutes. Motivate the scenario bank without previewing its answers.

    On-screen Voiceover / talking points
    Slide: "Five lessons build knowledge. The scenario bank, mentor-reviewed, is what earns Independent." "Everything in this video and in the five lessons builds your knowledge of these check areas — that's real, and it's worth having. But this course's target is Independent: being able to support a team through this, not just recognize it. That's what the mentor-reviewed scenario bank is for — seven applied scenarios, each scored against a mentor's watch-for list, not just a right-answer key."
    Slide listing the recurring thread: "Watch for a false-clean result — in every check area." "And notice the thread that ran through every segment just now: a clean-looking status that nobody actually earned. Watching for that isn't specific to any one check area — it's the habit this whole course is building."

    Call to action / close¶

    ~45 seconds.

    On-screen: Return to the cold-open screen recording, now showing the same task after a genuine review — status re-run, denied/blanket-approved items resolved. Closing slide: Lessons 1-5 → Scenario Bank (mentor-reviewed) → submit to your mentor.

    Voiceover: "That's the shape of it: a spiral of checks, a final turn that can't assume earlier stages caught everything, and one thread — the false-clean result — showing up in a different disguise in every check area. Work through the five lessons at your own pace, using each Challenge section to check your own recall. Then take on the scenario bank: write out how you'd diagnose each situation, what you'd say to the team, and what you'd escalate, and submit your answers to your mentor for review."

    Notes for the presenter¶

    • This is an orientation, not a tutorial. Don't attempt to run every check to completion on camera. The lessons carry the click-by-click depth and the Challenge exercises; this video's job is to make the five check areas and the false-clean thread familiar before a learner starts.
    • Per-lesson clips. If a fuller walkthrough of any one lesson is wanted later (Lesson 4 in particular, at 85 minutes of content, is the densest), record it as a separate clip rather than lengthening this overview past ~18 minutes.
    • Terms to define on screen, not just say: false-clean result (cold open and every segment), Correct/Incorrect/Undecided vs. denied (Segment 2 vs. Segment 4 — these are genuinely different mechanisms and are easy to blur together in speech), grey tick vs. green tick (Segment 5).
    • Gaps flagged / confirm before recording:
    • The cold-open demo needs one concrete, reproducible live project state (denied error with strikethrough + View > Denied messages toggle, or a blanket-approved wordlist). Confirm which is easier to stage reliably on camera; both are field-confirmed in the lessons, but this script does not commit to one.
    • Segment 2's "down arrow stepping through occurrences" and Segment 5's grey-tick → green-tick approval and batch-approval (of breaks the team has already confirmed — the team confirms before anything is approved) are described generically here based on the lesson text; confirm the exact live sequence (which project, which term/word) before recording so the demo doesn't require last-minute UI hunting on camera.
    • Numbers/measures (Segment 3) is explicitly in flux — the new consolidated check was still in testing as of this course's design notes. Confirm with Jenni/Doug which check is actually available in whatever project is used for the recording before filming that portion, so the demo doesn't show a check state that contradicts the lesson text.
    • The Punctuation Inventory / Unmatched Pairs of Punctuation menu paths (Segment 4) were corrected more than once during this course's SME fact-check (see 00-design.md) — confirm the exact menu path against the presenter's own Paratext version immediately before recording, since these are exactly the kind of detail that drifts between versions.
    • PTXprint UI (Segment 5) was verified against PTXprint 3.0.38 in the lesson; confirm the presenter's installed version before recording and note on screen if menu labels have moved.
    • This script does not invent any UI screenshot beyond the screenshots in assets/ and what the lesson files already describe — where a live recording is called for instead of a still, that's a deliberate choice to show motion (e.g. down-arrow stepping, click-to-approve), not a gap in the source material.
    • Live-demo caution: several of this course's field cases involve settings that are easy to get wrong on camera (denying a Basic Checks error, resetting a wordlist to Undecided, editing hyphenation break marks) — rehearse each live segment on a disposable/test project first, not the recording take.
